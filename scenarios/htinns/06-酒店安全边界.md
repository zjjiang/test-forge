# 酒店安全边界 业务描述

> 用户场景 5 的安全部分，拆成独立哨兵场景（2026-11-05）：专职盯防越权与非法输入，不与日常主链路混跑——哨兵红了单独处理，不污染主场景红绿灯。

## 环节

1. **店侧登录并配信科凭证**：复用固定夹具店 E2E-读写-1105-134852（shop_id=113，密码 123456），配平台 ID 499 + Cookie（XK_COOKIE）
2. **新增真实酒店并信科同步**：弹窗填 `HOTEL_NAME`（信科平台真实在线酒店）→ 点「信科同步」→ 字段回填断言（供应商/SHID/HID 非空）→ 保存入库；打上「白名单」标签（供非法提交后比对不变）
3. **越权编辑他店酒店被404**：店侧会话直接 POST `/hotels/<他店酒店id>/update`（目标为新乡旅途真实酒店，id 走项目变量 `OTHER_HOTEL_ID`）→ 期望 **404**，不泄露他店酒店存在性；只读探测，绝不写真实店
4. **非法标签值被拒**：POST `/hotels/tag` 带 `status_tag=恶意标签<script>` → 期望 **302** 回列表 + danger flash「非法status_tag: …」→ 夹具酒店标签仍为白名单（非法提交不落库）
5. **收尾删除真实酒店**（teardown）：行内删除按钮清掉哨兵酒店并断言无残留

## 数据纪律（v4，2026-11-05 用户明确）

哨兵酒店不再用编造的 E2E-哨兵酒店（假 SHID），改为**信科同步新增的真实酒店**（HOTEL_NAME，与场景 03 同源），带真实 SHID/HID。打白名单、越权探测后的标签比对都在夹具店内进行，收尾删除，不影响真实店铺。

## 口径备注（源码核实）

- 越权编辑：`_shop_hotel_or_404` / `update_hotel` 中「不存在或不属本店一律 404」
- 打标校验：`tag_service.set_hotel_tags` 校验顺序为 shid 非空 → **值合法性** → 酒店存在性，故非法值用占位 shid 即可命中值校验分支
- 两个 http 探测复用 shop actor 登录态 cookie（`http` 步骤原生支持）
